# pint #2551 — Cross-class Quantity assignment in `__setitem__`

> Units library correctness · 3 files · +24/−1 · merged November 4, 2026

## Outcome

[PR #2551](https://github.com/hgrecco/pint/pull/2551) fixed issue [#826](https://github.com/hgrecco/pint/issues/826): assigning a plain `Quantity` into an array whose class is a `Quantity` subclass — or the other way around — raised a nonsensical error for a valid assignment. Maintainer `andrewgsavage` merged the PR.

## Problem and diagnosis

The failing assignment raised

```text
DimensionalityError: Cannot convert from 'meter' to '1 / meter'
```

even for a plain same-dimension assignment. The cause is in `NumpyQuantity.__setitem__`: the fast path tested `isinstance(value, self.__class__)`, so a value of a different `Quantity` class fell through to the fallback branch, which builds the value with reciprocal units — the source of the inverted unit in the error message. Widening the check to `PlainQuantity`, the same test the NaN pre-check in the same method already uses, sends cross-class assignments down the normal conversion path.

## Result and validation

After the fix, same-dimension assignments work across classes, including unit conversion (e.g. `cm` into an `m` array), and a genuinely different dimension raises the intended `DimensionalityError` message. The new `test_setitem_subclass` in `pint/testsuite/test_numpy.py` covers subclass-array/base-value, base-array/subclass-value, a cm→m conversion, and the mismatched-dimension error; it fails on the unfixed code and passes with the fix. `test_numpy.py` and `test_quantity.py` went from 833 passed before to 834 passed after (16 skipped, 1 xfailed both ways); `test_issues.py` and `test_errors.py` passed 218 tests. A CHANGES entry is included, and the CodSpeed benchmark report showed no performance change.

## What I learned

An error message that makes no sense — converting 'meter' to '1 / meter' for a meter assignment — is usually a sign that the input took a wrong branch, not that the conversion itself is broken. Here, two checks inside one method disagreed about the type contract: the NaN pre-check asked "is it a plain quantity at all?", while the fast path asked "is it exactly my class?". The stricter check quietly routed valid inputs into a fallback built for a different case.
